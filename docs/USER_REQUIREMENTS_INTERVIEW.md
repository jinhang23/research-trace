# 用户需求访谈（持续更新）

日期：2026-09-03。状态：主要需求访谈完成，已形成 [融合方案](FUSION_PLAN.md)；用户授权后已完成 [Entire 本地隔离验证](ENTIRE_POC.md)，真实 UF 接入待验证。用户要求先询问实际需求，再据此选型；此前 Frappe / MLflow 推荐是访谈前的候选分析，不是确定方案。

## 使用情境

用户以 vibe research 为主：自己理解项目、把握方向，具体探索和实现主要交给 AI。希望无感留下人可读、语义清楚、精炼连贯的研究记录，同时使 Agent 获得经验、找到未探索方向，并能用子 Agent 检查和纠错。

典型项目已开发一年，涉及蛋白质–配体合成数据生成、亲和力预测、多种预训练策略及消融实验。代码、数据、输出、记录与版本很多，现状难以溯源，需要依靠个人记忆甚至昂贵重跑。成功和失败探索缺少总结，不能有效指导后续研究。

代码、数据、实验输出与 AI 对话均在 UF 超算。用户明确使用 Claude Code 开展 AI 开发。作业通过 SLURM 提交，实验通常接入 W&B。现有目录结构见下文，实际路径与 Git 仓库边界尚未检查。

用户进一步说明：一般创建一个新目录，让 Agent 在里面尝试不同版本的模型代码，再配置训练脚本，从各个版本的代码启动训练。每个模型版本的文件夹内包含训练脚本，公共代码放在外层，公共代码本身也可能修改。不能预设每个模型版本都是一个 Git 分支或独立 worktree。

由此确定版本范围应同时覆盖模型实现、训练脚本和外层公共代码。实际 Git 仓库边界尚未检查；若位于同一仓库，可用同一个代码 revision 表达整套代码状态。模型文件夹名本身不足以标识一次运行所用版本。训练提交需关联当时的代码状态，开发过程与未运行探索的版本记录也需要保留；具体检查点频率仍待确定。后续已完成本地合成项目的代码副本运行验证，真实 UF 作业固定版本与隔离仍待实现。

## 已明确的产品要求

- 自动采集并整理，尽量无额外手工记录负担。
- 2026-09-04 补充硬约束：整理只使用现有 Claude Code 订阅内额度，不另付模型 API 费用、不自动转额外付费。额度不足时保留材料并等待。用户仍希望保留 fork，也接受先保存材料再单独调用；具体后台方案尚未实施。
- 随后用户明确选择方案 3：独立整理模型接收新增材料、简短项目背景和相关旧记录，维护自己的上下文/缓存，不再以继承主会话完整上下文或共享其缓存为默认目标。优先复用现有项目源码；选型和复用范围见 [Recorder 复用方案](RECORDER_REUSE_PLAN.md)。这是已选方向，当前 alpha.26 运行实现尚未迁移。
- 记录问题、想法、选择理由、尝试、结果、纠正和后续可能方向；尚未执行的想法也值得记录。
- 研究含义可以围绕一组探索或实验总结，不要求每个动作或实验节点都有一份解释。
- 默认阅读精炼连贯、细节适量；需要核查时能找到对应材料。
- 用户认可当前 Web 界面，继续用现有界面浏览、检索与纠正记录。保留主要产品交互，在此基础上接入版本和实验来源；不要求重做为另一套产品界面。
- 长期追溯尤其重要：项目后期仍能定位早期决策和执行依据，降低靠记忆重跑的成本。
- 保留脚本、数据和结果的可定位依据，支持检查与有条件的复现；不能将“自动建立所有步骤的完整依赖图”作为必要前提。
- 关联可能缺失。记录应保留其独立价值，将未知关联标为待核实，不能补造确定关系。
- 希望代码改动与 Git 记录关联，并支持不同参数、实验和研究方向并行开展。快照时机、分支粒度和运行隔离方式仍待询问。
- 最大化复用已有成熟能力。当前 W&B、SLURM、Git 工作流应纳入选型依据。
- W&B 的默认职责仅为 loss、准确率等指标和曲线；研究记录节点链接到对应 W&B 实验供查看。用户不希望用 W&B 管理代码，只有没有合适替代能力时才考虑作为备选。

## 对上一轮需求草案的修正

“串起完整依赖”表述过强，改为尽可能保留可靠的关键证据关联，允许局部缺口。研究含义主要在一组探索的层次表达。细节可按需查阅，默认展示不应过度展开。

用户明确首版从启用时重新开始记录，不需要处理既有一年历史。历史回溯由用户主动提出，届时可把回溯内容补成研究节点。自动批量历史扫描、导入或旧项目重建不属于首版要求。补录设计应标明来源、补录时间和已知的事件时间，保留无法确定的信息；不要把事后整理伪装为当时记录。

首次接入可读取当前工作区以建立代码基线，自动采集的起点应清楚；启用候选工具时应核对默认行为，避免无意导入此前会话。历史回溯是显式触发的单独动作。

## 并行版本管理：已核实的能力与待定设计

Git 本身支持同一仓库多个工作目录，同时检出不同分支，见 [git worktree 官方文档](https://git-scm.com/docs/git-worktree)。因此“Git 只能对应一个目录”不构成重新实现版本控制系统的理由。

设计上需要区分代码版本与运行配置：同一代码版本可以对应多次不同参数的运行；修改代码的研究方向可以使用独立工作目录。用户希望它们在研究记录里形成可理解的并行探索关系，具体工作方式尚待确认。

W&B 已有代码 artifact、未提交修改 diff 与跨 run 代码比较能力，见 [保存和比较代码](https://docs.wandb.ai/models/app/features/panels/code)，但用户明确不希望默认使用这些能力。后续选型以 W&B 指标和链接边界为准。提交时固定代码与配置、作业运行期间避免代码变化是待验证的设计要求，不是已实现能力；worktree 本身不是不可变运行快照。

针对用户提出的“面向 Agent、类似 Git 的工具”，访谈时核实了以下候选。后续优先验证了 Entire；没有把三者选为一套组合，也未验证互相兼容：

- [GitButler](https://docs.gitbutler.com/ai-agents/overview)：提供 Agent 可调用的 CLI、按文件/变更片段组织提交、并行与堆叠分支。其[并行 Agent 文档](https://docs.gitbutler.com/ai-agents/parallel-agents)明确支持一个工作目录的多个活动分支，但文件系统和运行状态共享，不是训练隔离机制。
- [Entire](https://github.com/entireio/cli)：将会话、修改文件与 Git 提交关联。当前 README 描述 manual-commit 策略，工作中有临时 shadow 状态，用户或 Agent 提交时形成持久 checkpoint；不会自动在活动分支上替用户提交。因此无感记录是否充分，仍取决于提交时机和原始历史留存。不能据此保证所有未提交探索长期可恢复。
- [Jujutsu / jj](https://github.com/jj-vcs/jj/blob/main/docs/working-copy.md)：Git 兼容的版本控制工具，多数命令执行时自动保存工作副本状态，支持多个 workspace。不是持续监听每次文件修改，也不直接提供研究语义总结。

用户现有“多个实现并存”的目录形式可以在一个仓库中表达；同一个提交可以包含多个模型实现。是否需要 GitButler 的逻辑分支或独立工作目录，要根据真实目录组织及并发修改方式决定。GitButler、Entire、jj 不应仅因为各自有相关功能就全部叠加使用。

## 实验执行的最终边界

用户选择“提交后保留原目录不变”，并明确这是研究 Agent 的工作。包含训练脚本的模型目录及实际
引用的公共代码由研究 Agent 负责保持稳定。记录系统不替 Agent 提交 Slurm、不复制执行目录、
不锁住目录、不重写训练路径，也不负责运行、取消或重跑实验。alpha.23 引入的 Submitit 执行职责
越过这个边界，alpha.24 已撤回。系统被动收集对话、工具命令/输出与代码证据，保留现有 Web。

## 访谈结论与实施阶段待核实事项

已明确模型目录含训练脚本、外层有可变公共代码，开发工具为 Claude Code；从启用时开始记录，历史回溯仅由用户主动触发；当前 Web 界面已被用户认可。主要访谈可以收束，接下来按融合方案验证上游接管能力。实际 UF 路径、仓库边界、同时修改公共代码的行为及宿主版本是接入时要检查的环境事实，不应继续作为泛化需求问卷阻塞方案形成。
