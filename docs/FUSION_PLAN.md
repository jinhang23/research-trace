# Research Trace：需求访谈后的融合方案

日期：2026-09-03。依据：[用户需求访谈](USER_REQUIREMENTS_INTERVIEW.md)。本分支已实现首批组件替换和运行捕获；实际用法与范围见[运行集成指南](RUNTIME_INTEGRATION.md)。UF 真实作业接入尚未验收。

**决定：保留现有 Web 产品，由 Entire 提供 Claude Code 会话与代码提交的关联，沿用 Git、SLURM 和 W&B；通用协议、渲染、布局及服务基础设施逐项用成熟库替换。**

这次访谈明确了原选型尚不知道的条件：用户已满意现有界面，实际宿主是 UF 上的 Claude Code，W&B 只需要曲线链接，允许部分来源关联缺失，记录可以总结一组探索，首次启用从现在开始。首版因此采用组件替换路线，取代此前 Frappe / MLflow 整体迁移的建议。

## 产品边界

研究节点承载一组相关探索的连贯说明：问题、想法、选择理由、主要发现、未探索方向及纠正。一个节点可以关联多个代码版本、多个作业和多个 W&B run；只有想法、没有代码或实验，也可以形成节点。

继续使用现有 Project / Overview / Chapter / Node、阅读详情和人工纠正体验。底层逐项替换时保留这些业务接口。默认阅读适量展开，细节以可点击的来源呈现，不要求每次工具调用或每个 run 都产生一段独立总结。

## 主要组件如何分工

| 职责 | 选用方向 | 本项目负责的差异 |
| --- | --- | --- |
| 人的阅读、检索、纠正 | 现有 Web | 更准确的节点组织、适量总结与来源入口 |
| Claude Code 会话与代码来源 | Entire，作为优先验证的上游实现 | 新记录起点、项目绑定、内容过滤、未提交探索覆盖、与研究节点关联 |
| 代码版本与差异 | Git 对象和提交；Entire checkpoint 关联上下文 | 自动留存时机、模型与外层公共代码的完整取样范围、训练版本固定 |
| 多模型并行探索 | 保留现有目录组织；有逻辑分支管理需求时再接 GitButler | 将研究方向、代码版本和实验运行关联；避免把目录名当唯一版本 |
| 集群作业 | 现有 SLURM | 小范围的提交/状态适配，保存 job ID、入口、实际配置及代码来源 |
| loss、准确率等曲线 | 现有 W&B | 节点保存 run 标识和 URL，不要求 W&B 保存代码或大文件 |
| 研究整理与经验调用 | Research Trace Recorder 与现有研究工具 | 按探索主题整理，区分想法/尝试/结论，提供有效经验与未探索方向，保留人工权威 |

[Entire 官方说明](https://github.com/entireio/cli)支持 Claude Code，并将会话和代码提交关联。当前策略是在用户或 Agent 提交时形成持久 checkpoint；上游不会替用户自动在活动分支提交。因此它是代码与会话关联的优先候选，不能未经验证就宣布替代全部原始采集、投递或研究记忆。

Entire 原生 checkpoint 与纯讨论、未提交或已放弃探索的留存是不同问题。后者必须可以独立进入研究系统。如果上游不能满足首次落盘前的过滤、未提交内容留存、离线恢复等要求，只接管满足要求的部分。适配层补明确缺口，不重新实现上游已有的版本对象、差异和会话关联机制。

## 用户实际工作流

1. **启用。** 选定项目，从启用时间建立当前代码基线和采集起点。读取当前状态不意味着批量回溯历史会话。
2. **讨论与探索。** Claude Code 正常工作；Recorder 判断是否有值得记录的内容，并归入相关研究节点。新想法没有实验结果也能被记录，重复操作无需反复扩写正文。
3. **代码变化。** 保存可引用的代码检查点，范围覆盖模型目录内的实现/训练脚本与外层公共代码。自动留存至少覆盖有实际代码变化的阶段和提交训练前的状态；具体宿主事件、提交策略及并发行为在隔离验证中确定，用户无需逐次手工记账。
4. **提交训练。** 将本次训练实际使用的代码状态、入口、配置、job ID 关联起来。后续公共代码修改不应影响已排队/运行作业使用的代码。实现时选择固定 revision 的运行目录或等价快照机制；普通分支名、可变 worktree 和当前目录都不构成不可变保证。
5. **看到结果。** W&B 继续显示曲线。记录系统从一组实验总结研究含义，节点链接到各次运行。数据与输出优先记录稳定版本/位置及必要校验信息；完整依赖图不作为成功前提。
6. **后续研究与纠错。** Agent 获取当前有效总结、未探索想法、已知失败和未处理纠正；人或子 Agent 可以沿来源检查。错误记录保留修订，不能让旧摘要再次成为当前结论。
7. **主动回溯。** 用户提出请求时再调查指定历史并补节点，区分事件时间、补录时间和来源可靠性。

数据路径可能指向可变文件，路径本身不足以承诺可复现。对于关键数据保留可得到的稳定版本或摘要；缺失时明确可检查与不可恢复的范围。首版不自动复制所有数据和模型权重，也不强制将现有训练流程改为全套工作流 DAG。

## 并行探索的选择

用户当前的组织大致是“项目公共代码 + 模型 A 目录/训练脚本 + 模型 B 目录/训练脚本”。这种并存结构可以直接由一个仓库记录。同一个代码提交可以包含多个模型，而不同参数运行可以引用同一个提交。

[GitButler](https://docs.gitbutler.com/ai-agents/parallel-agents)适合将同一工作目录的修改分配到不同逻辑分支。它明确共享文件系统和运行状态。因此首版不把 GitButler 设为运行隔离或溯源的必需依赖；只有实际出现需要分开提交、比较、合并的开发任务时再启用。与 Entire 的 hook/提交兼容性需要真实测试。

Jujutsu 是备选版本管理接口，首版不同时引入 GitButler 与 jj 两套操作体系。Git 与 Entire 是代码/上下文层的优先路线；模型并行运行通过明确的代码状态引用表达。

## 保留界面也可以减少自研基础设施

| 当前实现 | 替换目标 | 完成的判断标准 |
| --- | --- | --- |
| `mcp.py` 的手写消息和协议处理 | [官方 MCP Python SDK](https://github.com/modelcontextprotocol/python-sdk) | 六个业务工具与登录行为兼容，删除旧协议循环，而非长期双实现 |
| `webapp.py` 的自制 Markdown 解析器 | [markdown-it](https://github.com/markdown-it/markdown-it) | 保留页面外观、代码块和来源跳转，删除旧解析器 |
| 自制图布局算法 | [Dagre](https://github.com/dagrejs/dagre) 等现成布局库 | 保持章节分区、节点和交互，用库替换布局；不为此强制更换前端框架 |
| `storage.py` 的连接、通用数据访问及内嵌 schema 升级 | [SQLAlchemy](https://docs.sqlalchemy.org/en/20/tutorial/index.html) + [Alembic](https://alembic.sqlalchemy.org/en/latest/index.html) | 保留业务接口及初期 SQLite 后端，迁移后删除重叠访问/升级路径；人工优先规则仍是业务代码 |
| `auth.py` 中通用 OAuth 客户端流程 | [Authlib](https://docs.authlib.org/en/latest/oauth2/client/index.html) | 复用授权/令牌流程；角色、设备授权和项目访问仍分别验收，不能宣称整个权限系统自动被替换 |
| GitHub 定时备份 | 按用户要求移除 | 删除调度与 UI；保留手动导出/旧格式读取，不引入 restic |

上表除业务查询 ORM 化外已接入：MCP、Markdown、布局、OAuth 原有通用实现已删除；
SQLAlchemy 管连接、Alembic 管迁移，业务 SQL 保留。GitHub 定时备份直接移除。

现有 FastAPI 服务可继续作为业务入口。保留 Web 不等于所有后端都不可替换；但当前没有证据表明为了用户需要的体验，必须先迁移到一个完整业务应用平台。

## 首版不设为必要依赖的候选

- Frappe / Outline：当前 Web 已满足用户的主要交互偏好，首版采用更小的组件替换。未来若团队管理成为主要成本，再评估平台级替换。
- MLflow：用户当前只需要 W&B 指标与曲线链接；不为相同实验功能要求增加另一套平台。此前本地开发的 MLflow 导入保持可选，不能成为新用户启用的必要步骤。
- Basic Memory：此前已接通，仍可作为派生检索选项。是否默认启用取决于中文研究问题的召回收益、部署成本和权限表现。
- LangGraph / AiiDA：目前不要求多步骤工作流编排或完整计算依赖追踪，不作为启动条件。

## 必须由接管样例证明的行为

1. 模型 A 与模型 B 共享公共代码。A 提交后公共代码继续变化，再提交 B，两次运行能准确区分所用版本。
2. 只有讨论与未实施想法、没有代码提交的一轮，也能形成有依据的研究记录。
3. 一组多次实验汇总为连贯节点，不产生十几条重复语义记录；每次运行的引用仍可展开。
4. W&B 只保留现有指标流程，节点可跳转到对应 run，代码版本不依赖 W&B 保存。
5. 用户修订后，Recorder 不能覆盖更新的人工内容或擅自关闭纠正；Agent 读取的是当前有效版本。
6. 首次启用不导入旧会话；显式回溯才补历史节点。未知 parent/来源可以留空并说明缺口。
7. 断网、退出和重试不丢失已承诺持久化的材料，不重复创建业务节点。上游缺失功能应有明确回退而非静默伪装成功。
8. 从保留的代码/checkpoint/记录备份中恢复后，早期证据仍可读取。只有哈希、却没有保留对象或可取回副本，不算长期追溯完成。

当前提示已允许未知 parent、实验分组和未实施想法。节点来源改为按 ID 精确查询，缺失明确报告。
